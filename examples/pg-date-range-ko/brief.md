# 하루치 주문 조회로 배우는 B-tree 범위 스캔 브리프

이 예제는 스킬 사용법을 보여 주려고 만든 공개 예제다. 실제 서비스의 사건이 아니라 로컬 PostgreSQL 18에서 재현한 예제 상황이다.

## 주제와 목표

- 주제: 날짜 조건에 함수를 씌우면 왜 인덱스를 못 쓰는가
- 다 본 독자가 스스로 설명할 수 있어야 하는 것:
  1. 실행 계획에서 Seq Scan, Filter, Index Cond, Buffers가 무엇을 말하는지
  2. B-tree가 범위 조건을 어떻게 읽는지
  3. `date(created_at)` 조건을 인덱스로 읽으려면 무엇을 바꿔야 하는지

## 독자

- 누구인가: SQL은 쓰지만 실행 계획은 거의 읽어 본 적이 없는 백엔드 개발자
- 이미 아는 것: SELECT, WHERE, 인덱스를 만들면 빨라진다는 것
- 처음 나오면 설명해야 하는 용어: Seq Scan, Filter, Buffers, B-tree 리프, Index Cond, STABLE, IMMUTABLE

## 사용자가 준 구성 (원문 그대로)

> 느린 쿼리 하나를 사건 순서로 따라가며 실행 계획, B-tree, 함수의 변동성을 배우게 해 줘. 열 장 안쪽으로.

## 형식

- 분량: 10장 (처음에는 9장, 결정 기록 참고)
- 흐름: 사건 순서(상황 → 분석 → 원리 → 해결)
- 문체: 한국어 "~다" 평서문
- 숫자: 페이지 수처럼 흐름을 이해하는 데 필요한 것만 쓴다. 시간은 한 번 잰 참고값이라고 밝힌다.

## 근거

- 쓸 수 있는 자료: PostgreSQL 18 문서, 로컬 실험 결과(`evidence/labs/`)
- 로컬에서 재현할 수 있는 것: 테이블, 두 쿼리의 실행 계획, 함수의 변동성, 표현식 인덱스
- 확인할 수 없는 것: 다른 하드웨어에서의 실행 시간

## 제약

- 공개 예제다. 실제 서비스의 이름, 수치, 코드를 넣지 않는다.
